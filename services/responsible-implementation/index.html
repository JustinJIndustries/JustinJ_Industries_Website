Implementation approach

Built to work. Thoughtfully designed.

Review consent behavior, trace authorized cross-domain journeys and validate releases against explicit test cases. These examples show the implementation choices and evidence we agree before handoff.

Visitor journeys and acceptance criteria

  • Define keyboard paths, focus transitions and form error states for the agreed pages.
  • Check semantic structure and content hierarchy with automated checks and scoped manual testing.
  • Record third-party limits, findings and ongoing content responsibilities.

Measurement rules and data boundaries

  • Specify consent states, event schemas and authorized domain handoffs before configuration.
  • Keep names, email addresses and contact-form messages in contact systems and out of analytics event payloads.
  • Link tagging checks, network evidence and known limitations to the release build.

Three implementation reviews.

Consent gating, an authorized booking handoff and build-specific QA each pair implementation choices with evidence.

Consent execution example

Make the selected consent mode observable.

A service business wants optional analytics to start only after the required visitor choice.

Policy choice for this example

Basic consent mode: withhold optional Google tags until the required consent is granted. The project owner approves the mode, categories and withdrawal behavior before implementation.

Implementation

Gate loading and firing by the approved categories. In a GTM consent template, use setDefaultConsentState before tag execution and updateConsentState for the CMP choice. Review custom tags alongside built-in consent checks.

Before choice or after decline
Pass: the network log shows no optional Google-tag resource or collection request under this basic-mode gate. Fail: a request appears before the required grant. Check the agreed endpoint inventory, including first-party collection routes.
After grant
Pass: Tag Assistant shows the consent update before the permitted tag event, with only approved categories firing. Fail: an event precedes the update or an unapproved tag fires.
After withdrawal
Retest future tag firing and the agreed storage cleanup. Fail: a newly disallowed tag fires after the acknowledged change. Record in-flight requests separately.

Technical references: Google consent modes and consent implementation.

Cross-domain example

Validate the handoff from site to booking.

A business authorizes measurement across its marketing site and a separate booking domain. Run the continuity test with matching permitted consent within the same test session.

  1. Business sitewww.example.com
  2. Linker handoff_gl
  3. Booking sitebooking.example.net

Implementation

Use the same Google tag ID from one GA4 web stream on both authorized domains and configure the intended cross-domain matches. Check that links, forms and redirects preserve the linker parameter through arrival.

Linker and session
Pass: a redacted network trace shows the linker arriving, with the expected client_id and session_id continuity. Fail: a redirect strips _gl or an unexpected new user/session appears.
Referral and attribution
Compare page_location, page_referrer and the expected source across the handoff. Fail: a self-referral or booking/payment domain incorrectly takes attribution.
Unwanted referrals
Review legitimate payment or workflow intermediaries separately. A referral exclusion changes attribution; it does not repair a broken linker or session handoff.

Technical references: GA4 cross-domain measurement and unwanted referrals.

Release QA example

Tie every check to the release build.

An application changes routes and submits inquiries without a full reload. Define expected events and test cases against one identified build.

  1. SPA page views

    Technical check

    Exercise first load, client-side navigation and back/forward. Choose one page-view mechanism: GA4 automatic history measurement or a deliberate GTM/application route trigger.

    Pass/fail evidence

    DebugView and request traces show one intended page_view per tested navigation, with updated location/referrer. Duplicate, missing or stale-route events fail the case.

  2. Payload schema and timing

    Technical check

    Check event names, value types and the field allowlist. Exercise rejection, validation error, confirmed success and retry paths.

    Pass/fail evidence

    An accepted inquiry produces the expected event once. A failed attempt produces no completion event. Wrong types, early firing, duplicate completions or personal/free-text fields fail.

  3. Regression record

    Technical check

    Repeat affected routes, keyboard journeys, responsive layouts and consent cases. Record the commit/build, browser, viewport and reproducible steps.

    Pass/fail evidence

    Case results, screenshots and traces correspond to the release build, with limitations recorded. Missing retests or evidence from an older build leave the release unverified.

Technical reference: Google SPA measurement and validation.

Agree the test contract

Record the selected consent mode, authorized domains, event schemas and critical visitor journeys. Agree acceptance criteria, required access, test data and review responsibilities.

Keep evidence tied to the build

Link test cases, redacted request traces, screenshots and known limitations to the release commit or build. Retest affected cases when code or configuration changes.
